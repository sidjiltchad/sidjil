# Sidjil Translation Integration Assessment

## الوضع الحالي

سِجِل Cloudflare Worker (`src/index.js`) مع D1 (`DB`) وR2 (`FILES`)، والصفحات العامة تُولّد من `src/views.js` مع نظام i18n قائم في `src/i18n.js`. الملف الأصلي يُخدم عبر `/file/:id`، وصفحة المادة تجمع الوصف والملفات وPDF والتفريغ والترجمة القديمة داخل عارض واحد. الجلسات الحالية في `admin_users` و`sessions` وتبقى كما هي.

## نقاط الدمج

- زر `ترجمة` داخل عارض PDF، والتفريغ، ووصف المادة.
- `src/translation.js` لواجهة المزود وAPI الخفيف وقراءة حالة Job والتنزيل.
- `migrations/0027_translation.sql` لجداول Jobs وكاش النصوص والإحصاءات والإعدادات.
- خدمة `translation-service/` لمعالجة PDF/OCR خارج Worker.

## القرار المعماري

يُستخدم SHA-256 الموجود في صف `files` كبصمة المحتوى. ويُشتق fingerprint من البصمة واللغات وإصدارات المحركات ونمط الإخراج وOCR. يوجد قيد UNIQUE يمنع Jobs المكررة. النتيجة المشتركة لا ترتبط بهوية الباحث، مع احترام صلاحية المادة قبل إعادتها.

تُترجم النصوص عبر `OllamaTranslationProvider` الذي يستدعي FastAPI محمية برمز خدمة. أما PDF/OCR فلا يعملان داخل Worker؛ يرسل Worker Job إلى FastAPI، وتعيد الخدمة مراحل التنفيذ إلى endpoint داخلي.

## حدود المرحلة الحالية

واجهة PDF وJob contract جاهزان. المعالجة الفعلية تستخدم خدمة Docker محمية برمز خدمة، ويقرأ Worker المصدر من R2 ويستقبل الناتج عبر مسارات داخلية محمية، لذلك لا تحتاج الخدمة إلى مفاتيح R2. ينتج المحول النصي PDF مترجمًا أو ثنائي اللغة صفحةً بصفحة، بينما إعادة بناء تخطيط PDF الأصلي بدقة تحتاج Adapter متخصصًا مثل PDFMathTranslate أو BabelDOC.

## الترتيب

1. تطبيق migration ونشر Worker.
2. اختبار ترجمة نص قصيرة مع Ollama `qwen3:8b`.
3. نشر خدمة المعالجة داخليًا وتفعيل PDF/OCR.
4. تشغيل اختبارات cache وdeduplication ثم إضافة مؤشرات لوحة الإدارة.
